# 标签推荐排序

项目编辑页复用 `GET /role-tags` 搜索接口。联想结果显示 emoji 和文字，选择后仍通过原项目 `tags: string[]` 保存纯文字，自定义输入、5 个标签及每项 12 字限制不变。无需接口或数据库结构变更，无需执行 SQL 迁移。

## 匹配规则

- 去除首尾空白、忽略英文大小写，合并重复标签。只识别标签库中的已知 emoji + 文字组合；不删除自定义标签中任意 emoji，不做模糊或语义匹配。
- 首先按双方同名标签的交集数量降序，包括自定义标签。
- 同名数量相同时，比较角色向量的余弦相似度。每个去重后的库内标签给关联的有效角色均分 1 份贡献；关联全部有效角色的通用标签不贡献角色分。多方向标签共同组成向量，结果取整到百万分之一。自定义标签不贡献角色分。
- 两项相同沿用原顺序。推荐匹配只在 `school_priority` 生效，不影响其他排序方式。匿名请求保留原排序。

## 项目

基准为登录用户的名片标签。没有标签时跳过库查询和项目标签查询，并保留原排序。

保持地域池、专业等级、热度晋级、补池、单池交换和同作者降池的计算。以上步骤完成后，只在同一最终池和专业等级的位置之间交换项目。原有同作者避让、关键词和赛事匹配优先级继续生效，因此这些约束可能使高标签匹配的项目不紧邻排列。

## 人才

基准依次为：

1. 本人创建、未删除、状态为 1/3/5（已发布、完成招募、已结束）的全部项目标签并集。
2. 没有这些项目时使用本人名片标签。
3. 基准为空时按候选人去重后的有效标签数量升序。存在已发布但无标签的项目时不回退名片。

保持原地域/专业/认证分级及热度晋级。标签次序位于两个原有 tier 排序表达式之后、随机顺序之前。

## 查询与验证

匹配在后端分页前执行。角色库批量读取，项目标签按候选 ID 一次批量读取；人才只预读符合现有筛选条件的 ID 和标签数组，计算后使用一个参数化 JSON_TABLE 表连接分数，SQL 完成排序及分页。没有逐候选数据库查询。数据规模增长时可根据实测引入缓存；当前不增加可能过期的用户标签缓存。

数据库使用已有标签库迁移所要求的 MySQL 8.0+。`tag_matching_test.go` 覆盖规范化、角色、优先级、无标签分支、分池及 SQL 参数顺序；`tag_matching_integration_test.go` 使用连接级临时表验证实际 SQL 与跨页结果。

PowerShell 验证命令：

```powershell
go test ./internal/repository ./internal/handler ./internal/service
# 可选：只指向一次性测试数据库，使用自己的本地测试连接串。
$env:KUAIZU_TAG_TEST_DSN = 'root@tcp(127.0.0.1:13317)/tag_matching_test?parseTime=true&charset=utf8mb4'
go test ./internal/repository -run TestTagRankingMySQL -v
Remove-Item Env:KUAIZU_TAG_TEST_DSN
```

客户端验证：在 miniprogram 目录运行 `npx tsc -p .. --noEmit` 和 `node --test tests/project-tag-selection.test.mjs`。开发者工具中应检查搜索、选择、重复过滤、逐项移除、自定义、保存后回显、搜索失败和输入过程中旧请求返回的情况。
