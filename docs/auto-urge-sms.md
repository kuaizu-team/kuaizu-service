# 名片投递量与自动催处理短信

## 名片投递量
项目详情接口返回可空的 `applicationCount`，统计该项目当前保存的全部 `project_application` 记录（所有状态，不含橄榄枝）。撤回后已删除的记录不计入，不是历史累计次数。使用已有项目索引，仅在详情查询中统计，不增加列表查询开销。客户端显示 0；旧后端未返回时显示 —。

## 部署
1. 人工审核并执行 `sql/migration_auto_urge_sms_state.sql`。程序不会自动建表或修改数据库。
2. 沿用现有消息中心配置和 URGE_PROCESS 模板；设置 `AUTO_URGE_SMS_ENABLED=true` 并重启后端。默认关闭；缺少状态表时记录日志并停用自动任务，其他 API 继续工作。
3. 无需额外 cron。服务每天北京时间 10:00 扫描，启动不立即补发；服务需要在扫描时间运行。多个实例依靠数据库主键及条件更新抢占，只有一个实例能对同一用户发起自动请求。

## 规则
- 未处理数 = 收到且 status=0 的橄榄枝 + 自己创建或当前加入的未删除、非删除中项目的 status=0 投递。创建者兼成员不会重复计数。已读但未处理仍计入，沟通中不计入。
- 未处理数至少 3 条，或最早一条当前未处理记录已满 168 小时，即满足条件；包含历史积压。
- 跳过封禁用户和无手机号用户。按用户 ID 每批 200 人，逐人发送前复核；单次扫描最长 2 小时，单次发送超时 30 秒。
- 自动发送成功后永久停止该用户的自动发送。后台手动发送接口与次数不受影响。
- 明确的号码、限流、余额、签名、模板或模板参数拒绝可在下一日扫描重试。未知错误码、传输失败、超时或不完整响应均视为结果不明确，不自动重试，避免消息实际已发出后重复发送。

## 留存与排查
独立表 `auto_urge_sms_state` 保存每用户状态、抢占标识、尝试次数、当时未处理数/最早时间、成功时间、消息中心记录 ID 和错误信息。结果字段允许空，不更改原有表字段或手动发送记录。

`ready` 表示复核后暂不满足条件；`failed` 表示明确未成功且可次日重试；`sent` 表示成功永久停止；`unknown` 表示结果不明确；`claimed` 表示请求正在处理或进程退出/保存结果失败。不会自动回收 claimed，也不会重试 unknown。请结合消息中心发送记录人工核对，不要仅因记录长时间未更新就删除或重置；需要再次催处理可以使用现有后台手动操作。

## 验证范围
单元测试采用 sqlmock 和模拟短信发送，覆盖并发抢占、明确失败重试、结果不明确不重试、保存失败、资格复核及北京时间调度。没有执行迁移、连接生产数据库或发送真实短信。上线前应在测试环境完成真实 MySQL 查询与消息中心联调。
